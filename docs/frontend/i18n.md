# Internationalization

## Scope and Terminology

The frontend uses `i18next` and `react-i18next` for application UI strings. Translation resources are shared by the Electron main process and the renderer so native UI, such as the tray menu, can use the same keys as React components.

These terms describe separate values:

- **UI locale**: the language used for XIV Megaphone labels, messages, settings, and native tray text.
- **Dialogue language**: language metadata received from the FFXIV plugin. It is separate from the UI locale.
- **Location**: a route location from React Router, such as `/settings`, or an external geographic location. Neither is used to choose the UI language.

## Locale Precedence

At startup, the main process resolves the UI language in this order:

1. A persisted language override is used when it is supported.
2. Otherwise, the operating-system language and preferred languages are checked.
3. The first supported base language is selected. For example, `fr-FR` is normalized to `fr`.
4. If none match, the UI falls back to `en`.

The main process initializes i18next with the resolved language and `en` as its fallback. The renderer obtains the resulting state over IPC before React is rendered, then initializes its own i18next instance with the same language and fallback.

## Persistence and Settings

The language override is stored in the Electron user-data configuration under `language`. Selecting any supported language writes an explicit override. Clearing the override returns the app to system-language resolution on the next initialization.

The Settings page displays the language selector in the Application section. The selector currently offers English, French, German, and Japanese. There is no separate system-language option in the current UI.

Changing the selector updates the main process and renderer together, including native UI such as the window title and tray menu.

The policy acceptance dialog uses the active UI language when displaying localized policy content. The dialog labels and the policy documents are separate translation surfaces.

## Process Responsibilities

### Main

`src/main/i18n.ts` owns startup resolution, the main-process i18next instance, and the authoritative `I18nState`:

- `systemLanguage` is the supported language resolved from operating-system preferences.
- `selectedLanguage` is the persisted override, or `null` when no override is selected.
- `language` is the effective language currently in use.

`src/main/index.ts` initializes this state before creating the window and uses the translation function when building the tray menu.

### Preload

`src/preload/index.ts` exposes only the required localization operations through the isolated `window.electronAPI` bridge. It does not load translations or read the configuration file. The type declaration in `src/preload/index.d.ts` defines the renderer-visible `I18nState` and the `SupportedLanguage | null` language input.

### Renderer

`src/mainview/lib/i18n.ts` requests the main-process state, initializes the renderer i18next instance, and installs the React integration. Components use `useTranslation()`. The language selector sends the requested language through IPC and applies the returned effective language to the renderer.

## IPC

The localization IPC surface is:

| Renderer method | Argument | Result | Purpose |
|---|---|---|---|
| `getI18nState` | none | `I18nState` | Read the effective and system languages plus the persisted selection |
| `setLanguage` | `SupportedLanguage \| null` | `Promise<I18nState>` | Persist or clear the override and update native UI |

The channels are `app:get-i18n-state` and `app:set-language`. The preload bridge forwards them to the main handlers; the renderer does not access Electron or the configuration file directly.

## Adding a Language

To add a UI language:

1. Add a locale resource under `src/shared/i18n/locales/` with the same shape as `en.ts`.
2. Register it in `src/shared/i18n/resources.ts` and add its code to `supportedLanguages`.
3. Add the code to `SupportedLanguage` and add its display name to `LanguageSelector.tsx`.
4. Keep `resolveLocale` normalization and the main, preload, and renderer IPC types aligned with the new code.
5. Update the resource-shape and locale-resolution tests.
6. Update this page with the supported code.

Adding a translation resource changes UI text only. It does not change dialogue language metadata or audio-processing behavior.
